## P0

None. Tenant scoping is present everywhere (`tenantId` filters in the new endpoints and service), date parameters are bound (not interpolated), and net/gross semantics are untouched (`totalNetProfit`/`totalGrossProfit` unchanged, new fields are additive — tests confirm).

## P1

1. **Settings lost-update race from the same Save click** — `views-settings-card.component.ts` `save()` fires `PUT /views` and `PUT /trader-commissions` concurrently via `Promise.all`. Both handlers (`settings.controller.ts`) do `SELECT settings → mutate one key → UPDATE whole settings blob`. Last writer wins, so one of the two changes is silently discarded on every save where both differ. Same race exists against the custom-columns card and any other settings writer. Fix: one endpoint that writes both keys, sequential saves, or a JSONB merge (`settings || $patch`) instead of read-modify-write.

2. **Trader-commission auto-fill is dead in the edit flow; deal-type change silently zeroes the commission** — `gateDealEconomicsFields` only fills when `body.traderCommissionPct === undefined`, but `order-save.service.ts` always sends `traderCommissionPct: (o as any).traderCommissionPct ?? null` — the key is always present. `onDealTypeChange` clears the pct locally on the assumption the server re-fills it ("the server re-fills it … server-side on save"), which never happens; `updateOrder` then persists the explicit `null`. Net effect: after any deal-type change, the commission snapshot is wiped and `tradingProfit` is silently overstated. Additionally the scheme lookup uses `(body as any).salesRepId ?? null` — on a PATCH that doesn't include `salesRepId`, the lookup targets `null` even if the other bug were fixed. Fix: treat `null` as auto-fill, and read the order's actual `salesRepId` from DB in the gate (or return the filled value and reconcile the client carefully — see autosave note in P2).

3. **Disabling the `deal-economics` view silently destroys stored data on any later save** — when the view is off, the gate forces all four fields to `null` on *every* create/patch, including patch bodies that never touched economics. Since the order-detail autosave always submits the full payload (and the DTO still returns the stored values, so the client echoes them), one unrelated edit to any order after the view is toggled off permanently erases TPC/pct data — which is explicitly "off-record" business data the spec says is snapshotted. Gating should hide/ignore, not null. Fix: when the view is disabled, drop the keys from the body rather than setting them to `null` (or only null them when explicitly provided).

4. **`getMonthlyHistory` period bucketing is broken/fragile** — `period` is `sql<string>` over `COALESCE(deliveredAt, eta)` and bucketed via `String(row.period).slice(0, 7)`. The cast is a lie: node-pg's default parser returns a `Date` for `timestamptz`, so `String(row.period).slice(0,7)` yields `"Wed Apr"`-style keys, `year`/`month` become `NaN`, and unrelated months collide (e.g. all January dates falling on a Wednesday across years share one bucket). If `eta` is a text/date column the `COALESCE` may instead fail at SQL level or produce locale-dependent strings. Fix: select `to_char(COALESCE(delivered_at, eta), 'YYYY-MM')` (or `date_trunc('month', …)`) in SQL and parse `YYYY-MM` explicitly. Verify against your actual pg type-parser config, but don't rely on `String()` of a driver value.

5. **Sensitive economics data is not view-gated or role-gated on read** — (a) `GET /dashboard/monthly-history` has the LIGHT-role guard but never checks `enabledViews` server-side; the 'performance-history' gate exists only in the Angular template. (b) `listOrders`/`getOrderById` now unconditionally select and return `tpcPerMt`, `tpcCurrency`, `traderCommissionPct` (and presumably the new economics) to every role that can read orders — so any trader (potentially LIGHT) can enumerate orders and reconstruct every trader's per-deal-type commission rates, which your own schema comment and spec classify as admin-only compensation data; TPC is also commercially sensitive by design ("off-record"). Fix: gate serialization on the tenant's `enabledViews`, and apply the same price-visibility masking to these fields/economics that you apply elsewhere for LIGHT users (verify existing masking actually covers the new fields).

## P2

1. **TPC currency default differs front vs back** — frontend `totalTpc` falls back to the order currency when `tpcCurrency` is null (`this.tpcCurrency() ?? this.currency()`), backend uses `normalizedCurrency(null)` (presumably USD). An order in EUR with a null TPC currency shows one "Trading" number on the detail page and another in list/history. Also confirm backend `totals.totalQuantity` and frontend `totalQty()` use the same quantity basis (ordered vs delivered).
2. **Turnover definition mismatch** — code uses `totalRevenueBase` while comments/spec say "gross invoice amount incl. VAT". Confirm whether item VAT/surcharges exist and whether `totalRevenueBase` includes them; either fix the metric or the comment.
3. **`ViewsService.load()` sets `loaded = true` before the request** — a failed first call (cold token, transient 5xx) permanently disables all views until reload. Also `views-settings-card` and the dashboard swallow all errors silently.
4. **No validation on commission config** — `rates: Record<string, number>` accepts negatives, >100, and `NaN` (which serializes to `null` in JSONB); view keys are arbitrary strings. Clamp rates and whitelist `['deal-economics','performance-history']` server-side.
5. **`order-financing-summary` shows the Trading block based on `hasCommissions()` (value presence), not on the view flag** — inconsistent with the stated "hidden when view disabled" behavior (and, combined with P1-3, fields will appear until the first save wipes them).
6. **Autosave ping-pong risk when fixing P1-2** — if the server starts re-filling `traderCommissionPct` and the client applies the response into the `order` signal, ensure your existing autosave watcher (the `skip(1)` subscription) doesn't treat the server-refilled value as a new user edit and re-save in a loop. Not yet introduced by this diff, but the intended fix path trips it.
7. **`monthly-history` loads all qualifying orders + items for all time on every dashboard visit** — fine at current scale, but consider a default `fromYear` server-side and/or caching; also `chartTicks()`/`chartPoints()` are called from the template and recompute on every change-detection pass.
8. **Verify imports not shown in the diff** — `isLightUser` in `dashboard.controller.ts` and `orders`/`orderItems`/`tenants`/`calculateOrderEconomics`/`getFinancingRateAnnual`/`inArray`/`notInArray` in `dashboard.service.ts`; no import hunks are present, so confirm the files compile. Minor: missing trailing newlines on the new components.

## Verdict

**Request changes.** No P0: no SQL injection, no cross-tenant leakage, and net/gross semantics are preserved exactly (well covered by the new unit tests — the EUR-conversion and negative-margin clamp tests are good). But there are five P1s that must be fixed before merge: the concurrent settings-save lost update (P1-1), the dead auto-fill + silent commission wipe on deal-type change (P1-2), the view-disable data destruction (P1-3), the broken monthly bucketing (P1-4), and ungated read access to commission/TPC data (P1-5). Note the order-list "Trading" column and migration 0117 weren't in the diff, so those weren't reviewable — confirm the list DTO applies the same gating/masking decided for P1-5.

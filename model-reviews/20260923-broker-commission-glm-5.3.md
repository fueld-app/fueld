## (2) Focus answers

**1. Precedence and `!= null`:** The line → order → tenant order is right (sibling + design-doc SQL agree). On the guard: `!= null` is the better primitive — null and 0 are different facts, the UI seeds null (not 0) for unpriced lines, so a stored 0 is more plausibly a deliberate "this line earns nothing" than an artifact; note your fix is at least *internally* consistent (tier 3 also uses `??`, so an intentional `defaultCommissionRate: 0` correctly wins over a stale legacy key). The defect isn't the choice — it's shipping two money computations for the same concept with different semantics (Finding 3). Unify both; don't leave it implicit.

**2. NaN:** Pre-existing for tier 1 (same column, same parseFloat) — but the fix adds two more unguarded sites and a new edge: `String('')` → `parseFloat('')` = NaN, which `?? 0` doesn't catch. And no, `sanitizeNumeric` (`orders.service.ts:1971`) guarantees nothing numeric: it nulls only `''`/`'null'`/`'undefined'`; `"abc"`, `"3,5"` pass verbatim into text columns. Whether TypeBox rejects non-numeric at the write boundary is unverifiable here, and imports/direct SQL bypass it anyway. Add the finite guard now (Finding 2) — it's one line against a whole-report-poisoning failure mode.

**3. Date fallback:** Pre-existing and tenant-configurable, not touched by this diff — but it now matters more because non-zero money flows into `createCommissionOrders`. Including the un-delivered example order means Moxie invoices commission on undelivered product. It's a product call (accrual vs earned), not a blocker for the rate fix — but raise it with Frederik before he invoices, and consider a per-row delivered marker. See Finding 5.

**4. Quantity basis:** Intended per current design; today moot for Moxie (`delivered_quantity` NULL on all broker items — switching basis now would report zero everywhere again). It becomes a real defect when partial deliveries exist and the field is written. Keep `quantity`, raise with the customer, plan the `COALESCE` switch. See Finding 6.

**5. Unit conversion:** Orthogonal in mechanism, **not** in consequence. Tier 1 is unit-consistent by construction (per-line rate is presumably per the line's unit); tiers 2/3 are per-MT. Pre-fix, a GAL line reported $0 — wrong but visibly broken. Post-fix it reports rate × gallons, wrong ~300× and plausible. The fix converts a loud failure into silent wrong money, and Moxie historically has GAL/M3 items — so the 69,085.37 impact figure itself needs a unit check before anyone invoices from it (Finding 1).

**6. Dead branch?** Not dead — API-created/imported broker orders and any UI path that fails to seed reach tier 3. The masking risk is largely defused by the hardened test plus a platform quirk: since Elysia/TypeBox 422s undeclared fields, a future settings rename that drops `defaultCommissionRate` makes `enableBrokerDeals(..., { defaultCommissionRate: 5 })` fail at setup — the test goes red instead of passing vacuously. Residual gap: the report still reads settings by hand-rolled key names; read them through the settings schema/type shared with `settings.controller.ts` so a rename breaks `tsc`, not a test.

**7. Multi-line/group-by:** No double counting in the visible code. Each order-item row is processed once, and per-line summation with a shared order rate is algebraically identical to (Σ quantities) × rate — 350+40 at $3 → 1,170 = 390×3. Mixed lines (one per-line rate, one order rate) resolving per line is the intended semantics. Only residual risk is SQL join fan-out duplicating item rows, which is outside the diff and unchanged by it.

**8. Do the tests defend?** Split verdict. The order-level test (~`:179`) is a true bug-reproducer: against the old service it resolves 0 and fails for the right reason, asserting both total and formatted string. The modified fallback test (`:150`) now fails against the old code for the right reason (0 ≠ 400) — but only *exercises* tier 3 if `createBrokerDeals` leaves the order rate NULL (Finding 4). The precedence test (~`:203`) does **not** defend this change: it passes against a fully reverted service; your 13/2 result is only consistent with a full revert in which the two failures are the modified test and the order-level test, not the precedence test. Keep it as a forward guard (it would catch an order-beats-line swap), but fix the attribution.

## (4) Verified vs unverifiable

**Verified by reading:** the fix resolves both described faults and matches the design-doc/sibling precedence; the example order (null line rate, order 3.0000, 80 MT) now yields 240; the modified fallback test and order-level test fail against `ca6929c3~1` for the right reason; the precedence test passes against a full revert and the "2 fail = the two new tests" attribution is inconsistent with the 13/2 count; `sanitizeNumeric` is a sentinel scrubber, not a numeric validator; `?? 0` doesn't catch `''`; per-line summation ≡ qty-sum × shared rate; the SELECT already exposes `unit` (Finding 1 is cheap to implement).

**Unverifiable here:** the 15/0 pass run, clean `tsc`, and the revert experiment (author claims — internally consistent except the failing-test attribution); whether `createBrokerDeals` seeds `orders.commissionPerMt`; whether any writer can persist non-numeric rate strings (TypeBox write boundary, import paths); whether Moxie's current Aug–Sep window contains non-MT broker lines, and whether 69,085.37 embeds unit errors; the impact figures and read-only-ness of the prod tunnel; the actual contents of `fd69d793`; aggregation/status-filter code and payload mapping outside the hunks.

## (5) Verdict

VERDICT: needs-fixes — The rate-resolution logic is correct, urgent, and should not be redesigned; ship it after three small things: (a) the one-query unit check on Moxie's in-window broker lines (or row-level unit flagging) so this doesn't replace "everything is visibly $0" with "some numbers are silently 300× wrong" inside a flow that creates real invoice orders, (b) the NaN finite guard across all three tiers, and (c) pinning the tenant-default test to a NULL order rate so it can't drift to tier 2 the way the old test drifted past the rename. Findings 3, 5, and 6 are alignment/product follow-ups, not blockers.

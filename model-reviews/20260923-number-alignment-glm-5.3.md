## (2) Focus items

**1. `Number` vs `parseFloat` — right choice, and this commit changes nothing here.** Correction to the premise: the deleted `num()` already used `Number` with the identical guards — the `parseFloat → Number` switch shipped in `016748cd`, and order-financing's old `parseNumber` already used `Number` too. So `c255e5d6` contains **zero** comma-decimal behavior change. Substantively `Number` is correct anyway: these are Postgres `numeric` columns, and `'3,5'::numeric` is a hard error (`invalid input syntax`), so a comma-decimal string cannot be stored or read back from them; the UI write path also can't produce one (`+'3,5'` → `NaN` → `|| null` → stored null). `parseFloat('3,5') → 3` is a *silent mis-parse* — strictly worse than failing closed to the next documented tier. (One micro-case where `Number` is more permissive: `'0x10' → 16`, but that's unstorable in `numeric` and matches what the UI's unary `+` already does.) Not a regression.

**2. `parseNumber` is observably identical for every in-domain input.** null/undefined → 0 both ways; blank → 0 both ways (old via `Number('') === 0`, new via `null ?? 0`); non-finite → 0 both ways; finite → same. No caller can observe a difference. The only runtime delta is for type-rule-violating values (booleans, arrays), where old returned 0 and the new path coerces — see Finding 3.

**3. The `|| → ??` change is exactly one input class wide.** Since `toFiniteNumber` maps blank/absent/unparsable to `null`, and old `parseNumber` mapped them to falsy `0`, **both** operators fall through on those — the guards are precisely what makes the migration surgical. The only reachable delta is a per-line `0`/`'0'`/`'0.00'` (and `-0`) when a nonzero order rate exists: old paid `orderRate × qty`, new pays 0 — the intended fix. The `?? 0` tail is unreachable on the `calculateOrderEconomics` path (param is a number) and live only for direct null calls, where it matches old output. `orderCommissionPerMt` being 0-instead-of-null is immaterial (0 was the tail anyway) — but its derivation `parseNumber(commissionPerMt) || 0` is the mechanism of Finding 1: a *blank* order-level rate collapses to 0 before any tenant-default tier could be consulted. Production impact today: **bit-identical** — Moxie has no stored per-line 0, so every currently computable number is unchanged.

**4. No reachable `undefined`.** The parameter default `= null` converts an explicitly-passed `undefined` to `null` (TS default-param semantics), `??` treats null and undefined alike anyway, and `item.commissionPerUnit === undefined` is absorbed by the `value == null` guard. The tail is defensive, not load-bearing — fine.

**5. Right home and right shape.** `lib/` is correct for a cross-module, dependency-free primitive. The null-returning contract is the *point*: a `toFiniteNumberOrZero` variant is unchainable with `??` and would reintroduce the absent-vs-zero ambiguity this commit exists to kill; `?? 0` at consumers is idiomatic and greppable. `if (x)` misuse is possible but no worse than the `parseNumber` era, and the doc comment states the contract explicitly. Do not add a second helper.

**6. The tests are honest — and the author undersells two of them.** #3 is the true regression guard against the `||` semantics, as claimed. But #4 (blank) and #5 ('NaN') are *not* padding: weaken `toFiniteNumber` — drop the trim guard and #4 fails (blank becomes a real 0 overriding the order rate, i.e., the original incident); drop `isFinite` and #5 fails (`NaN ?? orderRate` → `NaN` since NaN is not nullish, poisoning `grossProfit`). They pass pre-commit only because `||` + old `parseNumber` coincide with `??` + guards on those inputs; a test's value is what it pins, not whether it failed yesterday. #1/2/6/7 are characterisation but pin the shared contract both modules now claim. #7 (delivered qty) overlaps the report's e2e, but unit-pinning the mirror against a suite the author himself calls contention-flaky is the right call. Gaps: Finding 5's table test; no number-typed `0` case (only `'0'`).

**7. Same-class audit.** Rule: **same bug class iff a stored finite 0 is a meaningful business value for that column.** Applied: the `|| 1` conversion factors are legitimate (0 is never a valid factor; migrating to `?? 1` would zero quantities — the "fix" is worse); `parseNumber(commissionPerMt) || 0` is operator-indifferent (parseNumber never returns null) but is Finding 1's mechanism; `getEffectiveQuantity`'s delivered-0 handling must be verified (Finding 2) — delivered 0 means "bill nothing," the same meaningful-zero class. The remaining `parseFloat` sites in `reports.service.ts` can't be enumerated from this diff, but note `parseFloat` carries the incident's DNA everywhere: `'3,5' → 3`, `'12abc' → 12`, `'Infinity' → Infinity`, and it never returns null so it can't join a `??` chain — migrating money-adjacent sites is an improvement, but each site's 0-semantics must be re-decided, not mechanically swapped.

**8. The `'NaN'` claim is true where it matters.** Postgres `numeric` accepts `'NaN'` (long-standing; it even sorts above every non-NaN value) and `'Infinity'`/`'-Infinity'` since PG14; node-pg returns numeric as text, so the column reads back as the string `'NaN'`, which the guard correctly rejects. The `sanitizeNumeric` sub-claim is unverifiable from this diff (Finding 4) — but even if it were stricter, the guard is **not dead code**: NaN can arrive as a JS number (the `typeof === 'number'` branch), and any write path bypassing `sanitizeNumeric` (raw SQL, imports, the report→create-orders flow) can store it. Keep the guard; correct the comment only if the premise turns out false.

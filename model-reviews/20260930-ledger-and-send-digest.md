## glm MUST-1 — verified CORRECT and fixed
`outstanding` was `totalCost − totalPaid − totalReceived`. glm's arithmetic: on this PR's own test
numbers (cost 10,000; commission invoice 1,000; receipt 250) the true net position is 9,250 — they
still owe 750 of commission — but the code reported 9,750, an error of `K − 2R` that sign-flips at
R = K/2, and **at full settlement (R = K = 1,000) reported 9,000 against a payable of 10,000**:
understating what we owe by the entire commission, and getting *more* wrong the more the supplier
pays. The pre-existing prepayment branch made it worse: `outstanding = −totalPaid` then minus R, so
a receipt *increased* the amount shown as owed to us — the direction confusion `supplier_receipts`
exists to prevent, surviving at position level.

Root cause: the ledger nets the *settlement* of a receivable while never counting the *claim* being
settled. Fixed by **not netting**: receipts are reported (`totalReceived`, `receivedCount`) and the
payable stays `cost − paid`. My e2e assertion had encoded the wrong invariant
(`outstanding === before − 250`); replaced with `outstanding === before` at full settlement.

## Test-infrastructure findings — the hard part of this round

**`mock.module` is process-global and order-dependent, and two existing files mock modules
PARTIALLY.** `bun test` re-evaluates a module mock only when the module is FIRST imported, so
whichever file imports the app graph first determines the implementation for every file after it:

- `documents.mail.service.test.ts` replaces `../src/modules/auth/microsoft-oauth.service` with an
  object carrying only `acquireGraphTokenForUser`. Any later file that loads the auth controller
  then dies with `SyntaxError: Export named 'buildAuthorizationUrl' not found` — which is exactly
  what my three new tests did. The other two files that mock this module spread the original; that
  one did not. **Fixed there** (`...await import(...)` spread), as the module's own documented
  requirement.
- The same file replaces `../src/lib/email` with only `getSmtpConfig`/`getTransporter`, so
  `sendNotificationEmail` disappears for every later file. **Fixed the same way.**

These were pre-existing latent breakages that only surfaced because a new file grew a dependency on
those modules. Both are now consistent with the rest of the suite.

**Consequence for my own tests, accepted deliberately:** because a process-global mock owns
`src/lib/email`, no e2e test can assert what a SUCCESSFUL send transmitted — the transport is not
controllable from my file. I first tried a real in-process SMTP sink (`Bun.listen` + `SMTP_*` env),
which worked in isolation and proved the whole path (real MIME, real quoted-printable body, real
base64 PDF attachment) but could not work in the suite. So the tests now pin the seams that are
transport-independent, which is where the risk actually lives:

- the log row (`documentType`, `sentTo`, subject, attachment name), written *before* the transport
  is contacted, so it survives a transport failure — and a FAILED send asserts `sentAt` stays NULL,
  because marking a never-sent payable as sent is the loss mode the route exists to prevent;
- the stamp→DTO round trip (`sentAt`/`sentTo`, including that a resend overwrites);
- the route serving the PDF from the SAME renderer the send uses (direct-call comparison), which is
  what the no-drift claim rests on;
- the recipient rule as a pure function — 8 unit tests including determinism under two row orders.

Also corrected: my receipt-only-currency test was wrong. Receipts must match the invoice currency
(the route enforces it), so such a row can only come from outside the app (support SQL, an import) —
which is precisely the defensive branch — so the test now writes it directly instead of pretending
the API can produce it.

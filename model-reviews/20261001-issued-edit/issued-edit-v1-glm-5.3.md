## Answers

**1.** Yes — B is a separate defect, and the guards do not substitute for each other. B is *wrong state frozen at issuance*; A/C are *right state frozen, then drifted*. The edit-block would not have prevented B: the line was created at 08:37, *after* the 08:32 issuance — a block would have refused the corrective edit and left the wrong invoice standing. The issuance gate does nothing for A/C (state was correct at freeze). Take: **4** (money truth) → **5** (issuance gate) → **2** (edit block) → **3** (visibility), with 3's reconciliation component pulled into step 1 as the standing detector. Warn-only (1) is rejected as the sole measure: Case A proves the system actively contradicts a warning — the cap pays out the larger number while a toast says "invoice differs" — and warnings are client-side and raceable. Interim warn is acceptable for `delivered_quantity` only, pending trader-workflow validation.

**2.** Freeze stays. Restating in place means the same invoice number with different figures — the worst possible audit outcome, it breaks the customer's AP match, and it makes the `/verify` link certify a moving target. The codebase has decided this twice already (`savePaymentSchedule`'s refusal wording; the never-reuse number rule in `voidOrderInvoice`). Void-and-reissue is a complete correction path — A's 198.79 is billable today by voiding and reissuing at 7,079.24. "Live wins" would also require a post-issuance writer for `invoices.amount` (none exists, by design) and re-rendering stored PDFs, breaking byte-for-byte serving. Live legitimately wins only pre-issuance and in the voided invoice's replacement. The defect was never the freeze — it's that the order side pretends the freeze doesn't exist.

**3.** The frozen invoice. A receivable exists when the document is issued; collections off live lines chases money the customer has never seen (198.79), permits recording payments above the document, and ages buckets against non-receivables. What breaks the other way: `max()` was presumably built so over-delivery could be collected without a reissue — that is precisely the practice to end: if the lift changed, the customer gets a corrected document, not a larger demand against the old one. One honest caveat: while a split schedule is partially issued, sum(live invoices) understates the eventual total, so the basis must be *schedule-aware* (issued shares + pending tranches' expected shares) — never raw `max()` against lines. Once issuance is complete, invoice sum only, with any live-lines excess surfaced as "unbilled delta — void & reissue," never silently absorbed.

**4.** Issuance already rides the DELIVERED transition, so "require DELIVERED" is de facto true. The enforceable requirement is on the *anchor*: `deliveredAt` must be present at issuance (the trader just asserted delivery — the date should be known, and a future-dated `deliveredAt` at issuance deserves a hard look given the 10-24 blip), or the trader explicitly confirms the deadline is ETA-anchored. Pre-DELIVERED `deliveredAt` should display as provisional until then. Post-issuance `deliveredAt` edits belong in the F3 block — it is a due-date input like any priced field. C needs no restatement: 30/10 was correctly frozen for the state known at issuance; the fix is the live view and anchor provenance ("due 30/10 = delivered 09/10 + 21d"), not the invoice.

**5.** Confirmation gate is the primary fix; transactionality is not. In B, the mid-edit state was committed in the DB — a perfectly serializable read-and-insert would have frozen the same 368,400.47. The human is the only detector of "that is not the deal I meant," so: hard-refuse zero-amount/no-priced-line issuance; require explicit confirmation of the exact amount and due date *before* freeze and *before* the email leaves; optional staleness hint if lines changed within N minutes. A transactional read+insert is still correct hardening against true concurrency, but as hygiene — it is not B's fix.

**6.** Before any code: void & reissue INV-2026-0006 at the verified figure and contact Dan Bunkering — the only customer-visible money error live today. Then decide A (bill the delta via void & reissue, or revert the edit and accept 6,880.45 — until then the cap must be 6,880.45, which is what F2's fix enforces); C is internal only. Customer-visible: B now; A the moment anyone demands 7,079.24 against the 6,880.45 PDF. Internal: F2, F4, F6, C's divergence.

## Implementation order

0. **Ops, today:** B remediation + customer contact; A decision; one-off drift query across all four tenants (the zeros are unverified — F4).
1. **Money truth (F2):** `orderPayableBase` invoice-based (schedule-aware while tranches are unissued); collections/aging invoice-only. Ship the standing reconciliation in the same PR — any live-invoice order where |live lines − live invoice sum| > 0.005, or a due-date input changed post-issuance, gets flagged. This is the detector F4 never provided.
2. **Issuance gate (F1):** refuse unpriced/zero; confirm figure (amount + due date + anchor) before freeze-and-email; require `deliveredAt` or explicit ETA confirmation.
3. **Edit block (F3):** server-side refusal on all frozen inputs, wording mirroring `savePaymentSchedule`, message routing to void & reissue. `delivered_quantity` gets workflow validation first — if post-BDN quantity finalization is a real trader pattern, ship warn + one-click void&reissue for that field and block price/currency/terms/deliveredAt unconditionally.
4. **Visibility (3):** frozen-vs-live side-by-side with delta and CTA; due-date provenance on order and invoice.
5. **Can wait:** transactional issuance; F6 fallback policy (refuse or resolve by `invoiceId`, never re-render); guard extension tests.

**Highest-value first step:** step 0's void & reissue of INV-2026-0006. A guard shipped next sprint does nothing for the wrong document a customer is holding this week.
